# HackRL 연구계획서 v0

작성일: 2026-09-28

상태: 연구 설계 초안. 환경 변형의 실행 검증과 학습 실험은 아직 수행하지 않음.

## 1. 목표와 범위

기존 게임형 강화학습 환경에서 **의도된 제약을 어기는 동작을 발견하고, 반복해서 실행하며, 실제 목표 달성에 활용하는 능력**을 비교한다. 관심 대상은 단순히 더 짧은 경로를 찾는 능력을 넘어, 경계 처리·객체 수명·자원 검증 같은 구현상의 예외를 이용하는 행동이다.

GBGallery의 실제 게임 버그를 출발점으로 삼되, 상용 게임을 그대로 구동하는 대신 Craftax-Classic 등 기존 환경에 작은 코드 변형을 적용한다. 초기에는 단일 에이전트 온라인 RL을 다루며 LLM, MARL, 대규모 신규 게임 제작은 범위에 넣지 않는다.

연구의 중심은 다음 질문이다.

1. 같은 환경 예산에서 어떤 알고리즘이 유용한 예외 동작을 더 자주 발견하는가?
2. 발견한 경험을 안정적인 행동으로 학습하는 능력도 알고리즘별로 다른가?
3. 네트워크 크기와 기억 능력은 발견·활용·적응 중 어느 단계에 영향을 주는가?
4. 정상 플레이를 먼저 배운 에이전트는 예외를 더 쉽게 활용하는가, 기존 전략에 고착되는가?

**첫 목표는 소규모 환경에서 위 질문을 분리해 측정할 수 있는지 확인하는 것**이다. 새로운 일반 지능 척도나 보편적인 해킹 능력을 이미 정의했다고 주장하지 않는다.

## 2. 무엇을 ‘환경 해킹’으로 볼 것인가

실제 실행 환경을 M, 허용된 행동 인터페이스를 A, 사전에 정한 정상 동작의 계약을 C, 외부 과제를 G로 둔다. 계약 C는 원본 환경의 규칙과 구현을 근거로 작성한다.

- **계약 위반 사건:** A의 행동만 사용한 실행에서 C를 위반하는 상태 전이가 발생한다.
- **발견:** 학습 중 처음으로 해당 사건을 경험한다.
- **재현:** 학습된 정책이 별도의 평가 실행에서 해당 사건을 다시 발생시킨다.
- **활용:** 위반 사건이 과제 G의 성공, 시간 또는 자원 효율에 기여한다.

모든 실행은 실제 환경 M의 전이 규칙을 따른다. 따라서 해킹 여부는 M만으로 결정되지 않으며, **사전에 명시한 C와 실제 동작 사이의 차이**를 기준으로 판단한다. 놀라운 행동을 본 뒤 사후적으로 계약을 만들어서는 안 된다.

예를 들어 ‘제작대 근처에서만 제작할 수 있다’, ‘수확한 식물은 다시 성장해야 한다’, ‘잠긴 문은 같은 색 열쇠로만 열린다’가 계약이 될 수 있다. 반면 정상 규칙이 허용하는 도구 조합이나 우회 경로는 그 자체로 해킹 사례에 포함하지 않는다.

계약 위반과 목표 달성이 같은 에피소드에 나타났다는 사실만으로 활용을 입증할 수는 없다. 사건 로그와 버그를 막은 환경에서의 비교를 함께 사용한다. 활용은 모든 정상 정책보다 높은 성능을 내야 한다는 뜻도 아니다.

## 3. 근거와 환경 후보

### 3.1 GBGallery에서 확인한 것

GBGallery는 NetEase 게임 5개의 실제 버그 76개를 정리한 게임 테스트 연구다. 논문은 알려진 버그를 선택한 버전에 다시 도입하는 방식도 설명한다. 일부 게임은 바이너리만 제공되며, 모든 사례의 원인 코드나 재현 자산을 이번 조사에서 확보한 것은 아니다.[1]

아래 표의 왼쪽은 논문에 보고된 현상이고, 오른쪽은 **우리가 제안하는 전이 가능한 변형**이다. 현상이 유사하다고 같은 원인 코드라고 가정하지 않는다.

| GBGallery에서 보고된 사례 | 참고할 메커니즘 | 적용 후보 | 근거의 한계 |

크래시·표시 오류·움직임 불능은 첫 버전에서 제외한다. 관심은 에이전트가 행동을 통해 반복적으로 활용할 수 있는 동작이다. 이전에 논의한 Workshop Escape는 별도 아이디어이며, 확인된 기존 벤치마크나 GBGallery 사례로 취급하지 않는다.

### 3.2 초기 환경 선택

**주 환경은 Craftax-Classic으로 한다.** 자원·제작·생존이 연결되어 있고, 공식 기준 구현에 PPO, PPO-RNN, PPO+RND가 있어 환경과 알고리즘을 함께 새로 만드는 부담을 줄일 수 있다.[2][3]

MiniGrid는 계약과 사건 검출을 간단히 확인하는 보조 환경으로 둔다.[4] 모든 후보를 동시에 구현하지 않고, 아래 두 Craftax 후보 중 먼저 실행 가능성이 확인되는 것부터 진행한다.

### A. 경계 너머 제작

- **계약:** 제작은 실제 좌표상 인접한 제작대에서만 가능하다.
- **원본 구조:** `is_near_block`은 주변 좌표의 블록 종류와 지도 내부 여부를 함께 검사한다.[2]
- **제안 변형:** 해당 함수에서 내부 여부 검사를 제거하되 블록 종류 검사는 유지한다.
- **예상 메커니즘:** 위쪽 또는 왼쪽 경계에서 음수 인덱스가 지도 반대편 블록을 참조할 가능성을 이용한다. 실제 JAX 동작은 실행으로 확인한다. 양의 범위 초과까지 대칭적으로 감긴다고 가정하지 않는다.
- **초기 배치:** 접근 가능한 경계와 반대편 제작대를 배치하고, 정상적으로 제작대까지 이동하는 경로도 제공한다. 기본 랜덤 지도에서 자동으로 성립한다고 가정하지 않는다.
- **과제:** 지정 도구를 제작하거나, 해당 도구가 필요한 기존 목표를 달성한다.
- **사건 판정:** 제작 성공 시 독립적인 좌표 검사로 실제 인접 제작대가 없었는지 확인한다.
- **활용 판정:** 이동 시간 또는 목표 달성의 이득을 평가한다. 경계에 서 있었던 것만으로는 성공 처리하지 않는다.

일부 블록이 관측 범위 밖에 있을 수 있으므로, 단순한 용량 부족과 기억 부족을 구분해야 한다. 위치와 지도 크기를 바꾼 평가는 동일 메커니즘 내 일반화로 해석한다.

### B. 수확 후 성장 상태 초기화 누락

- **계약:** 수확한 식물은 정해진 성장 시간이 지나야 다시 익는다.
- **원본 구조:** 수확은 식물 타일을 미성숙 상태로 바꾸고 성장 나이를 0으로 초기화한다. 이후 식물 갱신은 나이가 600 이상이면 익은 타일로 만든다.[2]
- **제안 변형:** 수확 시 성장 나이 초기화만 생략한다. 같은 스텝의 식물 갱신에서 다시 익는지 확인한다.
- **초기 배치:** 첫 검증에는 충분히 성장한 식물을 제공해 600스텝의 사전 농사 부담을 분리한다. 자연 생성·재배에서 시작하는 버전은 후속 난이도로 둔다.
- **과제:** 정해진 기간 생존하거나 식량이 필요한 탐색·전투 목표를 달성한다.
- **사건 판정:** 독립적인 수확 시각 기록을 두고, 필요한 성장 시간이 지나기 전에 동일 식물을 재수확했는지 확인한다.
- **활용 판정:** 실제 식량 획득과 생존·목표 수행의 기여를 확인한다. 식량이 이미 최대일 때 반복 행동만 하는 것은 별도로 기록한다.

원본 보상에는 새로운 업적과 체력 변화가 반영되며, 같은 식물을 반복해서 먹는다고 업적 보상이 매번 추가되지는 않는다.[2] 따라서 사건 횟수를 과제 성능으로 대신하지 않는다. 반복 수확이 실제로 유용한 과제가 없으면 이 후보를 수정하거나 제외한다.

다음은 결과가 아닌 실험 가설이다.

| --- | --- | --- |
| 탐험 보너스가 도움이 되는가? | PPO+RND가 첫 발견 확률을 높인다 | 버그와 무관하게 맵을 더 많이 탐색할 수 있음. 기회 상태 방문과 발견 후 재현을 함께 측정 |

| 기억이 필요한가? | 관측에서 사라진 단서와 행동 순서를 유지하는 데 RNN이 도움이 된다 | 전체 파라미터 수 증가일 수 있음. FF/RNN 비교와 FF 크기 비교를 별도 실험으로 설계 |

예외가 매우 국소적이면 작은 PPO가 곧바로 활용할 수도 있다. 이때는 크기별 성능 차이를 억지로 만들지 않고, 단순 검증 환경으로 분류한다. 반대로 아무 방법도 발견하지 못하면 즉시 고차원 유연성 문제라고 결론 내리지 않고 기회 상태의 접근성과 탐험 난도를 확인한다.

## 5. 알고리즘과 비교 순서

### 단계 0: 환경과 측정의 실행 가능성

각 후보에 원본 규칙을 유지한 `fixed`와 한 가지 결함만 넣은 `mutant`를 만든다. 두 버전의 관측·행동·보상·초기 상태 분포는 동일하게 유지한다. 버그 플래그와 평가용 판정기는 정책 입력이나 보상으로 제공하지 않는다.

스크립트 행동으로 다음을 먼저 확인한다.

1. 정상 경로로 두 버전 모두에서 목표를 달성할 수 있다.
2. 의도한 예외 행동은 mutant에서만 계약 위반을 발생시킨다.
3. 사건 검출기는 변형한 조건을 그대로 재사용하지 않고 독립적으로 판정한다.
4. 무관한 정상 행동의 전이는 두 버전에서 일치한다.
5. 예외를 이용하면 적어도 하나의 설정에서 실제 과제 이득이 발생한다.

행동 마스크나 관측 전처리가 정상 규칙을 강제해 예외 행동을 막지 않는지도 점검한다. 이 단계가 실패하면 학습을 시작하지 않는다.

### 단계 1: PPO 대 PPO+RND

공식 Craftax 기준 구현을 사용하고, 정책·가치 네트워크 크기를 고정한다.[3] 이 비교는 탐험 방식이 발견과 활용에 미치는 영향을 보는 첫 실험이다.

- 정상 환경의 PPO 학습을 확인한 뒤 mutant를 처음부터 온라인으로 학습한다.
- 두 방법의 환경 상호작용 수, 평가 간격, 튜닝 예산을 맞춘다.
- RND의 내재 보상은 학습용으로만 사용하고, 평가 성능은 공통 외재 과제로 계산한다.
- 초기 파일럿은 조건당 학습 시드 3개로 오류와 난도를 확인한다. 확률 추정이나 우열의 최종 결론에는 사용하지 않는다.
- 본 실험은 파일럿의 분산·비용에 따라 시드 수를 사전에 정한다. 조건당 10개를 출발 예산으로 검토하되, 실패율이 높으면 넓은 불확실성을 그대로 보고한다.

처음부터 모든 환경·모델·시드의 조합을 실행하지 않는다. 한 후보에서 평가가 작동하는 것을 확인한 뒤 두 번째 후보로 확장한다.

### 단계 2: 같은 알고리즘 안에서 네트워크 크기 비교

우선 PPO에서 구현의 `layer_size` 후보를 **128, 256, 512**로 바꾸고 인코더 종류와 깊이는 고정한다. 이 값은 실험용 후보이며 최적 크기라는 근거는 없다. 실제 파라미터 수는 선택한 관측과 모델 구성에서 계산한다.

- 정책·가치 함수·공유 인코더의 파라미터를 중복 없이 보고한다.
- RND까지 확장하면 정책 크기와 RND 예측기 크기를 동시에 바꾸지 않는다. 보조 네트워크 파라미터는 따로 보고한다.
- 환경 스텝을 맞춘 결과와 실제 시간·연산 비용을 함께 제시한다. 큰 모델의 느린 실행을 숨기지 않는다.
- 기본 학습률로 먼저 비교하되, 같은 소규모 튜닝 예산을 준 결과로 순위가 바뀌는지 확인한다.
- 최종 평가 지도와 시드는 모델·학습률 선택에 사용하지 않는다.

단일 너비 실험에서 나타난 성능 차이를 곧바로 ‘규모에 따른 일반적 유연성 법칙’으로 해석하지 않는다.

### 단계 3: 기억과 학습 방식

| 비교 | 목적 | 해석상의 제한 |
| --- | --- | --- |
| PPO-FF 대 PPO-RNN | 부분 관측과 행동 이력의 영향 | 파라미터 수, 시퀀스 길이, 상태 초기화 조건을 함께 기록 |
| PPO-RNN 대 PQN-RNN | 정책 최적화와 Q 학습 계열의 차이 | 구현과 갱신 방식 등 여러 차이가 있으므로 단일 원인으로 해석하지 않음 |

PPO-RNN은 Craftax 기준 구현에 있으며, PQN 저장소에는 Craftax용 순환 모델 학습 코드가 있다.[3][5] PQN은 리플레이 버퍼나 타깃 네트워크를 사용하는 전형적인 DQN으로 설명하지 않는다. 두 방법의 차이를 경험 재사용 하나로 환원할 수 없다.

Dreamer 등 월드 모델이나 별도 계획기는 이후 필요성이 확인될 때 검토한다. 초기 구현 목록에는 넣지 않는다.

### 단계 4: 정상 학습 후 적응

고정된 정상 환경에서 온라인으로 학습한 체크포인트를 복제한 뒤, 정상 환경에서 학습을 이어가는 조건과 mutant에서 적응하는 조건을 비교한다. 처음부터 mutant에서 학습하는 조건도 함께 둔다.

이것은 **온라인 사전 학습 후 환경 변화에 대한 적응** 실험이다. 고정 데이터셋으로 사전 학습하는 실제 offline-to-online 설정과 구분한다. 원래부터 존재하지만 드물게 방문하는 예외를 발견하는 실험과도 구분한다.

Offline RL은 데이터에 예외의 전조·위반·성공 활용이 얼마나 포함되는지 통제한 데이터셋을 만들 수 있을 때 후속 연구로 고려한다. 관측 데이터가 두 환경에서 완전히 같다면, 데이터 밖의 전이 차이를 데이터만으로 식별할 수 없다. GCRL도 여러 목표 사이에서 예외 활용 기술의 재사용을 연구할 때 도입한다.

## 6. 평가와 로그

### 6.1 핵심 지표

| 단계 | 지표 | 보고 방식 |
| --- | --- | --- |
| 발견 | 예산 B 안에 첫 위반을 경험한 학습 시드 비율 | 여러 예산에서 발견 곡선과 시드별 결과 |
| 발견 속도 | 첫 위반까지의 환경 스텝 | 미발견 실행은 우측 검열로 처리. 성공한 실행만 평균 내지 않음 |
| 재현 | 별도 평가 에피소드의 위반 발생률 | 평가 시 탐험 설정을 명시하고 모든 방법에 동일한 규칙 적용 |
| 활용 | 실제 목표 성공률, 완료 시간, 생존 시간 또는 자원 비용 | 과제별 주 지표를 실험 전에 하나 정하고 나머지는 보조로 보고 |
| 정상 능력 | fixed 환경의 동일 과제 성능 | 일반적인 게임 실력 차이를 파악 |
| 적응 | 환경 변화 이후 성능 회복과 활용까지의 스텝 | 정상 과제 성능 유지와 함께 보고 |
| 일반화 | 새로운 지도·위치·매개변수에서의 재현과 활용 | 보지 못한 버그 종류로의 일반화와 구분 |

추가로 경계 접근·식물 발견 등 **기회 상태 방문률**과 방문 이후 위반률을 기록한다. 조건부 비율은 병목을 설명하는 진단 지표이며, 정책마다 다른 방문 분포를 보정한 인과 효과로 해석하지 않는다.

### 6.2 활용의 기여 확인

학습한 정책을 동결하고, 같은 초기 상태 집합의 mutant와 fixed에서 평가한다. 사건 직전·직후의 상태와 자원 변화를 함께 확인한다. 가능하면 동일한 유효 상태에서 해당 행동을 두 버전으로 분기 실행해 직접 효과를 검증한다.

전체 에피소드의 성능 차이는 버그 의존성을 보여주는 보조 증거다. 첫 분기 이후 상태와 확률 과정이 달라질 수 있고, 같은 난수 시드가 이후 궤적의 동일성을 보장하지는 않는다. 계약 위반 이후에만 가능한 비정상 상태를 fixed에 강제로 복사하는 실험은 유효한 비교로 취급하지 않는다.

### 6.3 재현성과 통계

- 독립적인 학습 시드와 평가 에피소드를 구분한다. 많은 평가 에피소드를 많은 독립 학습 실행처럼 취급하지 않는다.
- 학습·검증·최종 평가 지도 집합을 분리하고, 최종 평가를 보면서 과제 배치나 하이퍼파라미터를 수정하지 않는다.
- 시드별 결과를 공개하고, 본 실험에서 학습 시드를 단위로 불확실성을 추정한다. 평가 지도 변동은 계층적으로 고려한다.
- 0회 발견은 해당 예산에서 관측하지 못했다는 의미이며, 발견 불가능을 입증하지 않는다.
- 실패 실행과 중단 원인도 기록한다. 버그 판정 실패와 학습 실패를 구분한다.

필수 기록은 환경·알고리즘의 커밋, 변형 ID, 설정, 학습 및 평가 시드, 관측·행동 정의, 실제 파라미터 수, 누적 환경 스텝, 시간, 하드웨어, 체크포인트, 외재 과제 성능과 사건 로그다. 사건 로그에는 위반 종류, 스텝, 관련 위치·자원·직전 상태·행동을 포함한다. 렌더링 가능한 대표 궤적도 보존한다.

## 7. 진행 순서와 중단 기준

| 순서 | 작업 | 다음 단계로 넘어갈 조건 |
| --- | --- | --- |
| 1 | 원본 의존성 버전 고정, 정상 동작과 후보 함수 확인 | 설치 및 짧은 정상 실행 재현 |
| 2 | 후보별 한 가지 변형과 독립 판정기 작성 | 스크립트 정상 경로와 예외 경로가 fixed/mutant에서 의도대로 구분됨 |
| 3 | 실제 목표 이득 및 기회 상태 접근성 확인 | 단순 반복 사건을 넘어 과제상의 기여를 확인 |
| 4 | 첫 유효 후보에서 PPO/PPO+RND 파일럿 | 정상 과제 학습, 사건 로그, 발견·재현 지표가 작동 |
| 5 | 두 번째 후보로 확장하고 난도 동결 | 특정 지도 한 개에만 의존하지 않는 실행 가능성 확인 |
| 6 | PPO 크기 비교와 본 실험 예산 확정 | 파일럿 분산과 실행 비용에 근거한 비교가 가능 |
| 7 | RNN·PQN 및 적응 실험 | 앞선 결과에서 남은 질문을 명확히 구분할 수 있음 |

모든 방법이 즉시 성공하면 쉬운 검증 과제로 남긴다. 정상 이동 거리나 선행 자원 수집 같은 해석 가능한 난도만 조절하고, 의미 없는 비밀 행동열로 난도를 만들지 않는다. 모든 방법이 실패하면 스크립트 실행, 상태 도달성, 정상 과제 학습을 먼저 재검증한다.

첫 파일럿 전에는 총 GPU 시간이나 전체 연구 기간을 확정하지 않는다. 실제 처리량과 발견 분산을 측정한 뒤 예산을 정한다.

## 8. 기대 기여와 한계

가능한 기여는 작은 환경 변형 자체보다 **발견·재현·활용을 구분하는 측정 방법**, 버그 메커니즘에 따른 알고리즘 차이, 정상 능력과 예외 적응 사이의 관계를 보여주는 데 있다. 크기 증가가 효과가 없거나 단순 탐험으로 충분하다는 결과도 이 질문을 좁히는 데 유용하다.

다만 소수의 합성 변형 결과는 실제 게임 전체의 버그 탐지 능력으로 일반화할 수 없다. 실제 버그에서 모티브를 얻었다는 사실이 분포의 대표성을 보장하지도 않는다. 벤치마크의 범위, 인위적인 초기 배치, 관측 제약을 함께 공개해야 한다.

GBGallery는 게임 테스트를 위한 관련 선행연구이고, PPO/RND/PQN은 비교 방법의 기반이다. 기존 소프트웨어 테스트·탐험·게임 결함 활용 연구와의 포괄적인 신규성 검토는 아직 완료하지 않았다. 논문화 전에는 이 부분을 별도로 확장한다.
