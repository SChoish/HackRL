# HackRL 연구계획서 v2

작성·개정일: 2026-09-28

상태: 원본 소스와 기준 알고리즘을 검토한 설계안. 환경 변형의 실행 검증, 학습, 처리량 측정은 아직 수행하지 않았다. 아래 수치는 실험 후보와 예산이며 결과가 아니다.

## 1. 연구 결정

**Craftax-Classic을 바탕으로 온라인 실험부터 시작한다.** 초기 목표는 일반적인 ‘해킹 지능’을 점수화하는 것이 아니라, 의도된 제약의 예외를 발견하고 실제 과제에 이용하는 과정에서 어떤 병목이 생기는지 구분하는 것이다.

GBGallery의 공식 분류는 Crash·Stuck·Game Logic·Game Balance·Display다.[5] 이를 원본 메타데이터로 보존하고, HackRL에서는 구현 원인과 난이도를 별도 축으로 둔다. **오류 계열 3개 × 잠정 난이도 3단계, 총 9개 과제 설정**을 제안한다.

| 계열 / 결함 | 과제 ID | 설계 의도 |
| --- | --- | --- |
| R / H1: 철 재료 하한 오류 | R-E, R-M, R-H | 국소 제작 → 후속 채굴 → 다른 전제 준비 |
| B / H2: 지도 내부 검사 누락 | B-E, B-M, B-H | 경계 채굴 → 자원 활용 → 위치 정보와 도구 준비 |
| L / H0: 수확 후 나이 초기화 누락 | L-E, L-M, L-H | 연속 수확 → 식량 거점 활용 → 직접 식재·성장과 후속 활용 |

9개는 독립적인 버그 9개가 아니라 3개 결함의 과제 변형이다. Easy/Medium/Hard는 설계 가설이며 파일럿에서 재분류할 수 있다. H0의 쉬운 과제는 같은 행동 반복으로 해결되는 대조군으로 남긴다. L-M/L-H는 물·휴식·채굴 목표와 결합했을 때 식량 버그의 이득이 있는지 먼저 확인한다. **실행 가능성 → 과제 이득 → 학습 가능성**을 통과한 후보만 본 비교에 사용한다. 실제 게임 버그의 직접 재현이 아니라 보고된 오류 유형을 참고한 합성 변형이다.

분류·난이도·각 과제의 시작 상태와 목표는 [9개 과제 목록](benchmark_catalog_ko.md), 코드 변경과 판정기는 [버그 명세](bug_specifications_ko.md), 학습·스윕·데이터 규약은 [실험 프로토콜](experiment_protocol_ko.md)에 둔다. 이 문서는 연구 질문과 의사결정의 기준을 정리한다.

## 2. 문제 정의

정상 계약을 C, 과제를 G, 정상 전이 커널을 P₀, 변형 전이 커널을 P₁로 둔다. 정책은 양쪽에서 같은 관측 형식, 행동 집합과 과제 보상을 사용한다. 버그 ID, 버그 활성화 여부와 계약 판정기는 정책에 제공하지 않는다.

계약 위반 지시자를 다음처럼 정의한다.

$$
e_t=\mathbf{1}\{C(s_t,a_t,s_{t+1})\text{가 위반됨}\}.
$$

C는 결과를 본 뒤 만드는 설명이 아니라 원본 규칙으로부터 먼저 명세한다. 예를 들어 ‘철 1개가 필요한 제작은 철을 보유해야 한다’ 또는 ‘상호작용은 지도 안의 바로 앞 칸에만 영향을 준다’가 계약이다. 정상 규칙 안에서의 도구 조합·우회 경로는 그 자체로 계약 위반이 아니다.

- **발견:** 학습에서 첫 계약 위반을 경험함. 우연한 사건도 포함한다.
- **재현:** 동결한 정책이 별도의 평가에서 위반을 다시 발생시킴.
- **활용:** 사건으로 얻은 자원·도구가 실제 과제 수행에 기여함.
- **적응:** 학습된 정상 정책이 예외 동작이 있는 환경에서 행동을 바꿈.

모든 사건은 실제 실행 커널의 규칙을 따른다. 따라서 ‘해킹’은 MDP만의 속성이 아니라 계약과 실행 사이의 차이에 대한 명칭이다. 성공과 위반이 동반됐다는 사실만으로 인과적 활용을 입증하지 않으며, 사건 직후 효과와 패치 환경 평가를 함께 확인한다.

초기 학습 목적은 외재 과제 보상의 최대화다. 위반 횟수를 보상으로 주는 버그 탐지 에이전트와 구분한다. RND의 내재 보상도 버그 판정기를 사용하지 않는다.

첨부된 OpenAI 보고서는 위반 성공과 원래 과제 성공이 다를 수 있다는 동기로 사용한다. `{위반 없음/있음} × {목표 실패/성공}`을 모두 측정한다. 현재 과제는 게임 상태의 계약 위반이며, 외부 도구 권한·프롬프트 인젝션을 평가한다는 주장은 하지 않는다. 확인한 원문과 사례별 한계는 [과제 목록 §5](benchmark_catalog_ko.md#5-첨부한-openai-사례에서-가져올-것)에 둔다.

**처음부터 mutant에서 학습한 에이전트는 정상 규칙을 배운 적이 없다.** 그 성능은 예외가 있는 MDP에서의 학습 능력을 보여주지만, 배운 규칙을 유연하게 수정했다는 증거는 아니다. ‘flexibility’가 논문의 중심 주장이라면 정상 선행 학습 후 적응 실험을 핵심 결과에 포함해야 한다. scratch 실험은 그에 앞선 환경·학습 기준선이다.

## 3. 왜 Craftax-Classic인가

Craftax는 ICML 2024의 JAX 기반 RL 환경이며, Classic은 Crafter를 재구현한 버전이다.[1] 기존 자원·제작·상호작용 규칙과 PPO/RND/PQN 코드를 활용할 수 있다.[2–4]

이번에 확인한 Classic의 관측은 주변 7×9칸의 기호 정보와 재고·생존 상태 등으로 이루어진 1,345차원 벡터이며 행동은 17개다. **기호 관측이어도 전체 상태가 보이지 않는 POMDP**다. 넓은 지도에서 FF 정책이 실패했다고 표현 용량 부족으로 단정할 수 없다.

초기에는 작은 지도와 준비된 재고를 사용하는 과제로 정상 게임 전체의 기술 습득 부담을 줄인다. 주 비교에서 적의 무작위 출현을 끄는 등의 변경은 fixed/mutant에 동일하게 적용하고 기록한다. 이는 원본 Craftax 점수와 직접 비교할 수 있는 공식 설정이 아니다. 이후 통과한 변형을 절차적으로 생성한 지도와 원본 보상으로 확대한다.

## 4. 반증 가능한 질문

| 설명 | 예상 패턴 | 구분 실험 | 약해지는 결과 |
| --- | --- | --- | --- |
| 탐험이 병목이다 | RND가 첫 위반을 앞당기지만 공통 기회 상태에서의 학습 차이는 작음 | 전체 과제와 기회 상태 근처에서 시작하는 별도 진단 비교 | 기회 상태를 줘도 큰 차이가 유지됨 |
| 드문 경험의 학습이 병목이다 | 발견 이후에도 재현·목표 성공에 시간이 필요함 | 같은 고정 데이터셋으로 offline 비교 | 충분한 공통 증거에서 방법 차이가 사라짐 |
| 네트워크 용량이 관련된다 | 크기별 차이가 정상 과제 성능만으로 설명되지 않음 | 같은 PPO의 너비 스윕, fixed 평가, 후속 고정 데이터 비교 | 학습률 변경이나 정상 능력 차이로 순위가 설명됨 |
| 기억이 병목이다 | 공간 단서가 관측에서 사라질 때 RNN의 이득이 커짐 | local 관측과 정보가 보완된 진단 관측을 구분해 비교 | 정보가 충분한 조건에서도 같은 격차가 남음 |
| 정상 정책의 고착이 병목이다 | 정상 선행 학습이 기본 수행을 개선해도 예외 채택을 늦출 수 있음 | 정상 체크포인트에서 mutant/fixed로 분기, scratch 비교 | 기본 수행을 맞춘 뒤 적응 지연이 관측되지 않음 |

이 표의 대안은 서로 배타적이지 않다. 발견한 실행만 모아 정렬한 학습 곡선은 선택 편향이 있으므로 진단용으로만 사용한다. 기회 상태 진단이나 offline 공통 데이터 비교가 없이 ‘발견 이후 학습 능력’의 인과 차이를 주장하지 않는다.

## 5. 환경 설계의 고정 원칙

1. **한 버전에는 원인이 하나인 결함만 넣는다.** 같은 결함이 여러 자원에 영향을 주면 그 범위를 공개한다.
2. 숨겨진 특정 좌표·개체 ID·비밀 행동열을 버그 발동 조건으로 쓰지 않는다. 위치는 실행 조건일 수 있지만 조건 자체는 코드의 일관된 규칙에서 나온다.
3. fixed에서도 과제 달성이 가능해야 한다. 정상 경로를 막아서 버그를 강요하지 않는다.
4. 버그 사용 자체가 아니라 동일한 외재 목표를 보상한다. 사건 로그는 평가에만 사용한다.
5. 하나의 학습 실행에서는 결함 여부를 고정한다. 정상→버그 전환이나 에피소드별 혼합은 별도 적응 연구다.
6. 실행 여부와 이득을 스크립트로 검증한 뒤 RL을 돌린다. 의도하지 않은 다른 부작용도 사건으로 기록한다.
7. 쉬운 과제는 쉬운 대조군으로 남긴다. 특정 방법의 실패를 만들려고 조건을 사후 변경하지 않는다.

## 6. 알고리즘 선택과 스윕의 우선순위

첫 파일럿은 **PPO와 PPO+RND, 정책 너비 256**이다. 다음 비교로 **PQN-FF**를 추가한다. 공식 저장소에 FF/RNN Craftax 구현이 모두 있으므로, 처음부터 PPO-FF와 PQN-RNN을 비교해 기억 효과를 섞을 이유가 없다.[4]

크기 효과는 우선 PPO 안에서 128·256·512 너비를 비교한다. Classic 기호 관측과 공식 3-hidden-layer MLP 구조를 유지하면 actor+critic 파라미터는 각각 약 0.413M·0.957M·2.438M이다. 소스의 Dense 층으로 계산한 수이며, 실제 초기화한 모델에서도 확인한다. 관측이나 구조가 바뀌면 다시 계산한다.

PQN과의 비교는 알고리즘 전체의 성능 비교다. 정규화, 옵티마이저, 탐험, 갱신 빈도가 다르므로 이를 한 가지 학습 메커니즘의 인과 효과로 해석하지 않는다. PPO-RNN/PQN-RNN은 기억이 실제 병목으로 남을 때 추가한다.

주 스윕은 [실험 프로토콜](experiment_protocol_ko.md)의 단계별 예산을 따른다. 알고리즘×너비×관측×난도×선행 학습×보상×버그 종류의 전체 조합은 실행하지 않는다.

주장을 ‘어떤 방법이 예외를 잘 활용하는가’로 정하면 기본 알고리즘 비교를 우선하고, ‘정상 전략에 얼마나 고착되는가’로 정하면 폭 256 PPO의 정상→변형 적응을 대규모 크기/PQN 확장보다 먼저 수행한다. 단순 mutant 학습 표만으로 후자의 주장을 대신하지 않는다.

## 7. 온라인부터 오프라인까지의 연결

온라인에서는 누가 어떤 경험을 직접 얻는지 측정한다. 오프라인에서는 동일한 경험을 제공했을 때 무엇을 학습하는지 측정한다. 두 질문은 보완적이다.

첫 offline 확장은 R-M(H1)에서 **독립적인 버그 활용 궤적의 수**를 바꾸고 BC·discrete IQL·discrete CQL을 비교한다.[6–7] 버그 경험이 없는 데이터는 대조군이며, 증거 없이 예외를 알아내는 것을 필수 성능으로 요구하지 않는다. 다른 난이도와 계열은 이 실험 이후에 확장하며, 쉬운 과제 데이터에서 어려운 과제로의 전이는 별도 조건으로 둔다.

단편 경험의 조합은 이후 단계다. 성공 궤적 하나를 여러 파일로 잘라도 one-step TD 학습에 제공되는 전이 집합이 같으면 새로운 조합 과제가 아니다. 독립적인 행동 궤적 사이에서 연결 가능한 상태와 후속 행동의 지원 여부를 검증해야 한다. H1의 음수 재고처럼 정상 데이터에 없는 후속 상태가 생기면, 조합과 상태 일반화를 구분해야 한다.

Online 단계부터 재사용 가능한 관측·전이·episode ID·종료 원인을 저장한다. 그러나 모든 학습 스텝을 원시 float 벡터로 보존하는 것은 비용이 크므로, 균등 표본과 사건 중심 보관본을 구분한다. 데이터 설계의 세부 조건은 실험 프로토콜에 둔다.

| 기회 상태에서는 배우지만 일반 시작에서는 실패함 | 도달·탐험 병목이라는 증거 | 탐험 비교 확대, 용량 스윕은 후순위 |
| 공통 데이터에서도 차이가 남음 | 경험 획득 외의 학습 차이가 존재 | 용량·보수성·상태 일반화 분석 |

가장 먼저 구현할 것은 **세 결함의 최소 동작 검사와 Easy 3개의 fixed/mutant 쌍**이다. 이후 Medium에서 정상 경로와 실제 후속 활용을 확인하고, Hard의 준비·관측·시간 부담을 검증한다. R-M을 크기/적응/offline 실험의 우선 과제로 미리 지정하되, 학습 가능한 활용 과제인지 확인한 뒤 진행한다.

이 문서는 실행 계획이지 학습 실행 기록이나 사전등록 문서가 아니다. 대규모 학습·외부 연산 자원 사용은 아직 시작하지 않았다. 세 결함의 아홉 설정만으로 범용 벤치마크의 대표성을 주장하지 않으며, 관련 연구 전반에 대한 신규성 검토도 남아 있다.
